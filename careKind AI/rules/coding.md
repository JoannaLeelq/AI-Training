# 代码规范 — SOLID、DRY、KISS

适用于技术设计、编码和代码审查。遵循已有项目语言、工具、命名和架构；以下原则以降低实际复杂度和错误风险为目标，不要求为每个函数创建接口或类。

## 缩进与格式

- 代码缩进使用真实 Tab 字符，每级缩进一个 Tab，显示宽度为 4 个空格；不以四个空格替代缩进 Tab，不混用缩进空格与 Tab。
- 项目 `.editorconfig` 规定 `indent_style = tab`、`indent_size = 4`、`tab_width = 4`。格式化工具配置需与此一致；引入工具时核对它是否支持该要求，不静默改为默认空格缩进。
- YAML 的缩进不允许 Tab，使用 2 个空格作为格式必要例外。Markdown 文档使用空格；保留用于换行的尾部空格。语言/文件格式另有硬性限制时明确记录该例外。
- 对现有文件只调整当前变更涉及的格式，不为应用本规则顺手重写整个代码库。代码评审检查新增/修改代码的缩进一致性。

## 16 条研发执行规则

以下为 Joanna 指定的代码交付与审查标准，配合 SOLID、DRY、KISS 执行。

| 编号 | 规则 | 执行与验收标准 |
|---|---|---|
| CR-01 | Single Responsibility | 一个函数/模块承担一个明确职责，按变化原因拆分；同一规则改变应有一个权威修改位置，不迫使调用者了解无关职责。 |
| CR-02 | Clear Naming | 变量/函数名表达业务含义和行为；不使用 `a`、`tmp`、`data2` 等无法说明用途的名字。局部惯用索引须确实清晰。 |
| CR-03 | No Hard-Coded Secrets | API Key、密码、token 通过未跟踪的本地 `.env` 注入；生产可由受控环境/秘密管理服务注入。禁止放进源码、Git、日志、截图或文档。`.env` 文件必须被忽略；已经入库的凭证需撤销/轮换，新增忽略规则不会移除历史秘密。 |
| CR-04 | Comments First | 编写复杂逻辑前先写简短的“为什么”：业务限制、设计理由或重要不变量。代码变化同步更新注释；不以复述语句的注释替代清晰代码。 |
| CR-05 | Test-Driven | 身份归属、权限、签署状态、重试幂等、删除和关键转换等逻辑先写行为测试用例；至少在实现完成后立即补充并运行相关测试。缺陷修复增加可复现该缺陷的回归用例。未通过时不得记录为已验证。 |
| CR-06 | Explicit Error Handling | 错误显式抛出、返回约定错误结果或在责任边界处理；禁止空 `catch`、忽略失败或返回伪成功。对用户提供可操作状态；不在错误中暴露敏感内容。 |
| CR-07 | Validate at Boundaries | 在用户输入、外部 API/模型响应、文件导入和不可信持久化输入等系统边界验证并转换为可信内部类型。内部按已验证契约协作，避免逐层重复判空。授权、状态转换和并发约束属于业务不变量，仍在责任处执行。 |
| CR-08 | Secure by Default | 默认最小权限、拒绝越权、关闭未批准集成/采集/共享功能；放开范围须有明确配置、适用对象、依据和审计。配置缺失时安全失败，不使用宽松默认值。 |
| CR-09 | No Placeholder / Fake Data | 不将未完成 TODO、Lorem ipsum、假功能或编造业务数字作为完成交付；无真数据明确显示暂无/未知。待办单独记录，未实现范围如实说明。测试/模拟演示可使用明确标记、隔离的合成夹具，不冒充真实老人、客户反馈或产品成效。 |
| CR-10 | Performance Boundaries | 相关功能实现前明确可测的时延、容量、内存/队列和超时底线及测量环境；超出约定上限视为不合格。交互请求默认候选底线为代表性负载下 P95 ≤ 2 秒（客户端到服务端响应，注明测量口径）；批量上传/8 小时音频转写采用异步任务及 PRD 专属指标，不能保持同步请求等待全部完成。目标是验收门槛，不是未经实测的成绩。 |
| CR-11 | Minimal Dependencies | 优先标准库和已有依赖；引入新包前回答“是否确实需要、标准库/现有工具为何不足”，记录用途、维护/许可/安全成本。该判断不是每次都向用户重复申请许可；实际安装按已有权限执行。 |
| CR-12 | YAGNI | 只实现当前需求与必要安全/正确性控制；不为未来可能用到的模式添加接口、服务、配置或依赖。 |
| CR-13 | Code for the Reader | 以阅读者理解业务为优先：直白控制流、小而清晰的函数、明确副作用和合理组合；避免炫技压缩和难以解释的抽象。 |
| CR-14 | Explicit Types on Exports | 公开导出的函数明确参数和返回类型，导出的变量/常量明确类型，不依赖隐式推断。TypeScript 使用显式签名；Python 使用类型注解；无原生类型的语言用适用的签名/JSDoc/接口声明记录契约。内部局部变量可按现有语言规范使用类型推断。 |
| CR-15 | No any Unless Whitelisted | TypeScript 默认禁止显式/隐式 `any`，Python 禁止未经批准的 `Any`，避免以类型断言绕过真实校验。未知输入用 `unknown` 或适当未知类型并在边界收窄；必要第三方适配例外须经 Joanna 明确批准并登记 [any 白名单](any-whitelist.md)。没有记录就不允许。 |
| CR-16 | Refactor Above 1,000 Lines | 任一项目自维护代码文件超过 1,000 个物理行（包含空行与注释）时，自动触发重构，按职责拆分并去除真实重复，使原文件和拆出的文件均不超过 1,000 行。保持行为、公开契约、权限和数据完整性；运行相关回归测试后再交付。不能通过压缩语句、删必要注释或隐藏文件绕过阈值。 |

### CR-16 自动触发流程

1. 编码任务开始时检查涉及的代码文件；修改后、交付前再次统计新增/修改文件的物理行数。发现超过 1,000 行，直接将该文件重构纳入当前开发任务，无需为该规则重复请求确认。
2. 先识别职责、依赖和现有测试，补齐必要的行为回归证据；按 SOLID、DRY、KISS 拆分模块、提取有明确含义的复用，更新调用和导出。
3. 重构保持已有行为和对外契约，不顺带更改功能或放宽安全限制。遵循 Tab 宽度 4 和明确类型要求。
4. 统计重构前后各文件行数，检查新增模块的引用/依赖，运行相关测试与已配置的类型/构建检查。目标是降低单文件规模和复杂度，总项目行数不一定下降，不能为减少总行数牺牲清晰性。
5. 无法完成或验证时，记录具体阻碍、当前行数与剩余工作；不能把超限文件标为满足规范或把未通过的重构标为完成。

适用于自维护的源代码和测试代码；Markdown/PRD、数据、第三方/vendor 代码、锁文件和自动生成产物不按本条人工拆分。生成文件应在生成源处处理；排除项须说明性质，不能把普通源码标为生成文件规避检查。

## SOLID 的具体应用

| 原则 | 项目中的执行方式 |
|---|---|
| S — 单一职责 | 模块围绕一个明确变化原因组织；分离录音/上传、转写、身份归属、草稿、审核/签署及导出。避免一个服务同时处理身份、生成、权限和提交。 |
| O — 开闭原则 | 已存在的变化点，如转写供应商、机构模板、导出目标，通过小型适配器/配置扩展；不为尚不存在的需求建立通用框架。 |
| L — 里氏替换 | 可替换实现遵守相同输入/输出、错误、权限、取消和幂等契约；不能更换供应商后静默降低隐私或来源要求。 |
| I — 接口隔离 | 调用者只依赖所需能力；不要让转写模块依赖导出/签署/临床身份修改等无关方法。 |
| D — 依赖倒置 | 核心护理事件、身份校验和审核状态逻辑依赖明确契约，而非某家模型 SDK；供应商/数据库/网络细节放在边界适配层。 |

## DRY

- 同一业务规则只有一个权威实现：机构权限、resident ID 验证、状态转换、签署条件和字段映射避免各端各写一套。
- 客户端可做体验校验，但服务端必须执行权威安全/数据校验；这种分层校验不因 DRY 而取消。
- 提示词、模板和配置有明确版本与来源；不要复制硬编码后各自漂移。
- 抽取复用针对相同业务含义，不因两段代码外形相似就合并不同规则；小量重复有时比错误抽象更清晰。

## KISS

- 选择能满足当前需求和验收条件的最简单可维护方案，明确状态、边界和失败路径。
- 优先使用已有工具与清晰组合；没有已验证需要时不引入微服务、多级继承、自造框架或复杂调度层。
- 函数/模块名称描述行为，减少隐式副作用、复杂嵌套和隐藏全局状态；注释说明不明显的原因、限制与契约。
- 复杂度由真实约束驱动：8 小时音频的分块、恢复和幂等有需求依据，不能为了“简单”一次将整段无限制加载到内存。

## 产品与数据不变量

- 在服务端对每次数据查询、生成、回放、修改和导出验证机构及角色权限；模型输出不能授予访问权限或确认身份。
- 草稿、待确认、已签署和修订有明确状态；未经授权不能签署，签署版本不能静默覆盖。
- 模型输入视为不可信数据；输出经过 schema、ID、枚举、来源、时间和格式校验。不给模型直接提交正式记录的权限。
- 上传、任务重试、签署和导出按实际场景设计幂等与并发控制；状态未知时先核对，不盲目创建重复记录。
- 凭证通过被 Git 忽略的 `.env` 或受控环境注入；健康内容和录音不进入一般日志、错误堆栈或测试夹具。开发/演示使用明确标识且隔离的合成数据。
- 新依赖说明用途，核对许可与供应链风险；只在需求/缺陷需要时调整依赖或重构。

## 变更与验证

- 重要变更关联 PRD 需求编号、问题或技术依据；先读相关产品/法律规范及现有代码。
- 针对行为和风险选择检查：权限隔离、身份冲突、状态流转、重试不重复、断网缺口和数据删除等。小型纯文档修改无需完整应用测试。
- AI 模型/提示词/模板变更使用适当的已标注合成评估场景验证；不以单个好看的样例证明正确性。
- 代码审查检查职责、契约、重复规则、复杂度、异常处理和数据保护；避免将风格偏好当作缺陷。
- 报告实际运行的检查和结果；没有运行或失败的部分明确说明。涉及实际发布继续使用现有发布准入流程。
