# Product delivery

Input: a feature, bug, requirement or release-preparation request. Product Owner: Joanna. Developers: Lin, Gary, Windston; do not infer individual module ownership.

1. Apply `rules/product-and-legal.md` before product design or PRD creation/revision: read relevant local law research, compliance register and reference index, then relevant original file sections. Inspect the relevant sections of `docs/PRD_careKind_AI.md` and existing app files. State material assumptions; clarify only information that blocks a useful result. If no app implementation exists and no build was requested, produce requirements rather than inventing a technology stack.
2. Maintain shared requirements and product strategy in `docs/`; update the authoritative PRD rather than creating a second competing copy. Record target user, care setting, problem, scope, source, acceptance criteria, data handled and failure/fallback behavior. Include actual local legal-reference review and source-to-requirement mapping using `rules/templates/legal-reference-matrix.md`; mark pending applicability/approval. Keep input, AI draft, human review and final record distinct.
3. For implementation, apply `rules/coding.md` (SOLID, DRY, KISS) and make the requested change in `APP Development/`, following existing architecture. Use synthetic data. If intended purpose or data flow changes, read the relevant Company OS clinical safety/privacy policy and record the review still required.
4. Perform checks appropriate to the change and the 16 coding rules. Count relevant first-party code files before changes and new/modified files before delivery; files over 1,000 physical lines automatically require CR-16 refactoring to at most 1,000 lines per resulting file, with behavior preserved and regression checks. For critical logic, write behavior tests first or immediately after implementation; run relevant tests, type/format checks where configured, and verify required performance boundaries in a stated environment. Separate observed evidence from proposed tests and report anything not run. Pure documentation edits do not require application tests.
5. Deliver files and a concise description of behavior and limitations. For release preparation, evaluate the existing `Marketing & Operations/Company OS/06_pilot_release_gate.md`; leave human/regulatory approvals as pending unless evidenced.

Completion: requested deliverable exists, relevant checks are reported, unresolved assumptions are explicit. Preparing a release does not by itself authorise production deployment or real resident-data processing.
